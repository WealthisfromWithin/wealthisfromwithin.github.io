# Deployment

**Status:** current as of Wave 7.
**Target:** GitHub Pages, user site root (`wealthisfromwithin.github.io`).
**Pipeline:** `.github/workflows/deploy.yml`, on push to `main`.

---

## 1. Prerequisites

| Requirement | Value |
|-------------|-------|
| Node | 22+ |
| pnpm | 10+ (`packageManager: pnpm@10.33.3`) |
| Pages source | **GitHub Actions** — must be set in repository settings (TD-18) |

That last row is the one thing that cannot be configured from this repository.
If Pages is left on "Deploy from a branch", the workflow succeeds and nothing

## 2. The pipeline

```yaml
push to main
  ├─ pnpm install --frozen-lockfile
  ├─ pnpm lint          # eslint, 0 errors 0 warnings required
  ├─ pnpm typecheck     # tsc -b --noEmit
  ├─ pnpm test          # vitest run — 919 tests, 68 files
  ├─ pnpm build         # tsc -b --noEmit && vite build && node scripts/postbuild.mjs
  ├─ actions/configure-pages@v5
  └─ actions/upload-pages-artifact@v3 (path: dist)
       └─ actions/deploy-pages@v4
```

Every gate is blocking. A failing test does not deploy.

`concurrency: { group: pages, cancel-in-progress: true }` means a rapid second
push cancels the first deploy rather than racing it.

**Build output is not committed.** `dist/` is gitignored; the compiled artifact
stopped being the source of truth in Wave 1.

## 3. What `pnpm build` produces

Three steps, in order:

1. **`tsc -b --noEmit`** — types are a build gate, not a lint suggestion.
2. **`vite build`** — Vite 8 with Rolldown, target `es2022`, no source maps.
3. **`node scripts/postbuild.mjs`** — copies `dist/index.html` to
   `dist/404.html` and ensures `dist/.nojekyll` exists.

### Why `404.html`

GitHub Pages has no SPA rewrite rule. It serves `404.html` for any path that is
not a file, so shipping the built index under that name is what makes
`/integrations` resolve when someone opens it directly rather than navigating to
it. `base: '/'` in the Vite config is the matching half: asset URLs must be
absolute for a deep link to resolve them correctly.

### Why `.nojekyll`

Without it, Pages runs Jekyll, which ignores files and directories beginning
with an underscore.

## 4. Bundle composition

Measured on the Wave 7 build.

### First load — 13 chunks, 639.46 kB raw / 195.60 kB gzip

| Chunk | Raw | Gzip | Contents |
|-------|----:|-----:|----------|
| `vendor-react` | 274.28 kB | 86.21 kB | React, React DOM, React Router, scheduler |
| `index` | 127.42 kB | 37.26 kB | Shell, router, brief, selectors reached by the href allowlist |
| `vendor-dexie` | 103.92 kB | 33.87 kB | Dexie |
| `vendor-zod` | 64.64 kB | 17.23 kB | Zod |
| `mutations` | 35.72 kB | 8.94 kB | The 50 writers |
| `domain` | 14.82 kB | 4.43 kB | Entity schemas and policies |
| `content`, `calendar`, `state`, `db`, `primitives`, `clock`, runtime | 18.65 kB | 7.66 kB | Shared leaves |

Plus **65.72 kB / 22.67 kB gzip** of CSS.

### Deferred — 42 chunks

Every route except the Morning Brief is `React.lazy`. The demo seed is also
deferred: 60.35 kB / 17.57 kB gzip that loads only when a seed actually runs
(see [`DATABASE.md`](./DATABASE.md) §5).

### Vendor chunking

`manualChunks` in `vite.config.ts` splits by package rather than by size:

- **`vendor-react`** — React, React DOM, React Router, and the scheduler move
  together because they version together.
- **`vendor-dexie`** and **`vendor-zod`** stand alone.

The benefit is caching, not first-load size: an application change no longer
invalidates ~440 kB of dependency bytes for a returning visitor. See
[`docs/reports/PERFORMANCE_REPORT.md`](./reports/PERFORMANCE_REPORT.md) for the
before-and-after measurement.

## 5. Content Security Policy

GitHub Pages serves static files and lets nobody set a response header, so a
`<meta http-equiv>` in the built `index.html` is the **only** delivery available.

The policy is generated by `buildContentSecurityPolicy` in `src/lib/csp.ts` and
injected by the `sovereign-csp` Vite plugin, which is `apply: 'build'` — the dev
server is deliberately left alone, because Vite's HMR client and the React
Refresh preamble are inline scripts a correct `script-src 'self'` policy would
(rightly) refuse.

Shipped policy:

```
default-src 'self'; base-uri 'self'; script-src 'self';
style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self';
connect-src 'self'; manifest-src 'self'; worker-src 'self';
object-src 'none'; frame-src 'none'; form-action 'none'
```

| Directive | Note |
|-----------|------|
| `script-src 'self'` | No CDN, no provider SDK, no analytics. Everything executable is built from this repository |
| `style-src` keeps `'unsafe-inline'` | `index.html` carries an inline `<style>` that paints the obsidian background before the stylesheet arrives. Hashing it would turn a future edit into a silent white-flash regression, and inline *style* is a materially smaller risk than inline script, which is not allowed at all |
| `img-src` allows `data:` | The favicon is an inline SVG |
| `connect-src` | `'self'` in the public build. A build configuring `VITE_API_BASE_URL` or `VITE_LOCAL_AI_URL` gets those **origins** added — origin only, never a path, because CSP matches path prefixes loosely and a policy naming a path looks narrower than it is |
| `frame-ancestors` | **Emitted only in the header form.** Browsers ignore it in a meta tag, so clickjacking protection on Pages is *absent*, not partial. See [`OPERATIONS.md`](./OPERATIONS.md) §6 |

`connect-src` is derived from the same variables the adapters read, so the
policy and the code cannot disagree: a build that configures a Command API can
reach it, and a build that does not, cannot.

## 6. Build-time configuration

Every variable is **public**. `VITE_*` values are inlined into JavaScript that
anybody can read. There is no such thing as a private build variable here, and
nothing in the codebase reads an API key from the environment.

| Variable | Default | Effect |
|----------|---------|--------|
| `VITE_API_BASE_URL` | unset | Enables the `/sync` health probe against that origin, and adds the origin to `connect-src`. Must be `https:` (or loopback `http:`), with no userinfo, query, or fragment |
| `VITE_LOCAL_AI_URL` | unset | Enables the local model adapter. Must be a loopback host |
| `VITE_LOCAL_AI_MODEL` | `llama3.1` | Model name passed to the local runtime |

The public deployment sets none of them. That is why the shipped `connect-src`
is `'self'` alone and why `/sync` ships in the `Disabled` state.

### Configuring a Command API

```bash
VITE_API_BASE_URL=https://api.example.com pnpm build
```

Note what this does and does not do. It enables **one** manual button that sends
one credential-free GET to `/health`. It does not enable sync, does not
authenticate anything, and does not cause any request to be made on load.

## 7. Service worker

`public/sw.js`, registered by `src/lib/pwa.ts` in production only.

Network-first with a cache fallback: a successful fetch is copied into the
`sovereign-v2` cache and returned; a failed fetch falls back to the cached copy.
Navigations always resolve to the app shell, so deep links work offline. Only
same-origin `GET` requests are handled.

**Bump `CACHE` in `public/sw.js` when the shell changes.** The `activate`
handler deletes every cache whose key differs from the current one, so the bump
is what evicts a stale shell. A failed registration is swallowed — an offline
shell must never be able to break the surface.

## 8. Verifying a deploy

```bash
pnpm build
pnpm preview          # serves dist/ locally
```

Then check, in order:

1. **The CSP meta tag is present** in `dist/index.html`, and `connect-src`
   matches what the build was configured for.
2. **`dist/404.html` exists** and is byte-identical to `index.html`.
3. **A deep link resolves** — open `/integrations` directly, not by navigating.
4. **`/sync` reads Disabled** on an unconfigured build, and the probe button is
   off.
5. **No console CSP violation** on first paint or on opening the palette.
6. **The service worker registers** and the app loads with the network throttled
   to offline after one successful visit.

## 9. Rollback

Pages deploys are artifacts, not commits, so rollback is a redeploy:

```bash
git revert <sha> && git push          # preferred: the history stays honest
```

or re-run the last good workflow from the Actions tab (`workflow_dispatch` is
enabled).

There is **no data migration risk in a rollback**. The store lives in the
operator's browser, and Dexie versions are additive — an older bundle opens a
newer store, because no migration has ever dropped a store or a row. The one
thing a rollback does not undo is a Dexie version the operator's browser has
already upgraded to; that store stays at the higher version, which is safe
precisely because the migrations are additive.
